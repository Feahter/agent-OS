# Agent OS 实测驱动的 ROI 迭代组合

本文档把 2026-09-12 的 Luna 六节点真实调度结果转成可排期、可停止、可验收的迭代组合。排序依据是对“每个验证成功结果”的成本、时间和可靠性的预期改善，而不是功能数量。

## 实测基线

| 指标 | 基线 |
| --- | ---: |
| 模型 | `gpt-5.6-luna`，reasoning `low` |
| DAG | 6 个节点，6/6 成功，全部 1 次完成 |
| 并发 | 配置 2，实测峰值 2 |
| 墙钟时间 | 61.503 秒 |
| 节点耗时合计 | 90.825 秒 |
| 样本并发收益 | 约 1.48×，相对串行节省 32.3% |
| Input tokens | 109,624 |
| Cached input tokens | 15,626 |
| Output tokens | 349 |
| Total tokens | 109,973 |
| 成本 | 未知，`cost_complete=false` |
| 自动化验收 | 320 tests passed；ruff、mypy、compileall、`git diff --check` 通过 |

这组数据支持三个判断：

1. DAG 内的关键路径调度已经有效，当前首要矛盾不是“再加并发”。
2. 六个很小的任务平均每节点约 18,271 input tokens、58 output tokens，固定上下文成本过高，是最大的直接 ROI 机会。
3. 成本仍不可完整计量；在引入自适应策略前，必须先建立可比较、不会把未知值当成零的经济性基线。

## ROI 排序

ROI 排序同时考虑用户影响、覆盖面、证据置信度和实现成本。范围是规划估算，不作为工期承诺。

| 排名 | 计划 | 预计投入 | 目标收益 | 置信度 | 启动建议 |
| ---: | --- | --- | --- | --- | --- |
| 1 | [上下文与 token 降本](01-token-efficiency.md) | 1.5–3 人周 | 验证成功结果 token 降低 35%–55% | 高 | 立即启动 |
| 2 | [Resident 热路径收口](02-resident-hot-path.md) | 1–2 人周 | 降低空闲 I/O、控制延迟和状态不一致 | 高 | 与计划 1 并行 |
| 3 | [经济性观测与基准](03-economics-observability.md) | 1–2 人周 | 让后续每项优化都能计算真实 ROI | 高 | 先完成最小基线切片 |
| 4 | [Resident 安全多任务并发](04-safe-resident-concurrency.md) | 3–5 人周 | 独立任务吞吐提升 1.7×–2.5× | 中 | 队列压力达到阈值后启动 |
| 5 | [自适应调度与路由](05-adaptive-policy.md) | 4–8 人周 | 成本或延迟再下降 10%–25% | 中低 | 累积足够真实样本后启动 |

## 推荐执行波次

### Wave 0：两天内建立比较尺

- [ ] 从计划 3 完成固定基准清单、运行 ID、输入数据和结果快照格式。
- [ ] 冻结 Luna 六节点场景，保留并发 1/2 两组对照。
- [ ] 明确 token 完整、成本未知、成本估算三种状态，禁止混合统计。

### Wave 1：直接降本和低风险加固

- [ ] 执行计划 1，先压缩重复上下文，再扩大验证后复用。
- [ ] 执行计划 2，修复 waiting 高频探测、锁内 telemetry 和投影陈旧。
- [ ] 每个变更都用 Wave 0 的同一基准做前后对照。

### Wave 2：按需求扩吞吐

- [ ] 只有连续一周出现 `active_jobs >= 2`，或 p95 排队时间超过 30 秒，才启动计划 4。
- [ ] 先交付原子 claim/lease 和 workspace 互斥，再把 worker 数从 1 灰度到 2。

### Wave 3：用数据驱动策略

- [ ] 至少积累 30 个验证成功结果、覆盖 3 类任务和 2 个执行器后，启动计划 5。
- [ ] 所有策略先离线回放，再 10% 灰度；质量门槛下降立即回滚。

## 组合级硬约束

- [ ] 北极星指标始终是“每个验证成功结果”的 token、费用、耗时和人工介入。
- [ ] 成本未知不得写成零；估算成本不得冒充 provider 实测成本。
- [ ] 不降低 Reality Anchor、审批、保护路径、Artifact 契约和预算的失败关闭语义。
- [ ] 不通过增大模型、增加 Agent 或扩大并发掩盖上下文浪费。
- [ ] 不把 prompt、原始响应、凭据或项目路径写入可迁移遥测。
- [ ] 新复杂度应藏在深模块内部；保持 `do/status/approve/control/result` 和 `ResidentCoordinator` 的小接口。
- [ ] 每个计划都必须定义停止条件；未达到收益门槛时撤销策略，不继续堆叠补丁。

## 决策规则

- 优化同时降低 token 和耗时：直接进入候选发布。
- token 降低但耗时增加：只有“每个验证成功结果”的估算费用显著下降且延迟仍满足 SLO 才接受。
- 吞吐提高但单任务成本上升：只对有排队压力的 profile 开启。
- 指标改善但验证成功率下降：拒绝，不做加权抵消。
- 数据不足以判断：保持旧策略，继续收样本，不把不确定性包装成收益。
